# spec-driven-kit

This repo is the kit itself: an agentic development kit (neutral roles and workflow, generated adapters for Claude Code, Codex, OpenCode, Cursor and Gemini CLI, hooks, git-hook guards, verify engine, stacks), all shipped as one Go binary (`sdkit`, macOS, Linux, Windows) plus tools that set up the project side
(`<project-dir>` = `.sdkit/`, committed except its personal and generated files; plus `AGENTS.md`, the kit block in `.claude/CLAUDE.md`, and generated host files, hidden from git per clone) in other repos. It is not a consumer of the kit; nothing here is a project.

Orientation: `README.md` (overview), `docs/guide.md` (full guide), `CONTRIBUTING.md` (how to change the kit), `docs/README.md` (reading map).

## Layout

Go module `github.com/wecii/sdkit`. `cmd/sdkit/` is dispatch only (one file per command, registered in `init()`); the logic is in `internal/<package>` (one package per command family; `internal/hook` has one file per guard; `internal/stack` one file per stack). `kit.go` embeds `core skills agents adapters stacks templates`, so the binary is the whole kit; those directories also stay in the repo as real files (the Claude Code plugin installs from git). Test data in `testdata/`, the Windows smoke script in `tests/windows-smoke.ps1`. The design is in `docs/go-port/` (`01-architecture.md` has the package map).

## Rules for working here

- **Keep the kit generic.** No project-specific branch names, cluster names, service names or risk criteria in skills, agents, hooks, code or fixtures.
  Those come from the consuming repo's `<project-dir>/sdkit.env` (shared), `sdkit.local.env` (personal, read after it) and `project.md` at run time.
- **Never hardcode `.claude/` for project facts.** Code and hooks find the project directory with the resolver (`internal/project`: `.sdkit` with `sdkit.env`; pre-1.0 layouts are not looked at, a repo on one runs the last 1.x `sdkit upgrade --migrate` first); docs and skills say `<project-dir>`. `.claude/` is literal only for Claude Code's own files (`CLAUDE.md`, `settings.local.json`, copy-mode `agents/ skills/ hooks/`).
- **Never overwrite project-side files** in `sdkit init` (`project.md`, `sdkit.env` (it only appends new settings), `rules/`, `settings.json`), not even with `--force`.
- **Hooks are off by default**: an empty setting means exit 0 silently. A hook only blocks on a deliberate decision, never because of its own error: `recover()` at the entry, and an error, unreadable JSON or panic ends as exit 0 with no output. Hooks are guards registered in `internal/hook` (one file per guard, `Register(...)`); Stop hooks check `stop_hook_active`.
- **`core/roles/` is the source of truth for roles.** `agents/` and `adapters/<host>/agents/` (codex, opencode, cursor, gemini) are generated by `sdkit dev adapters` (per-host emitters in `internal/emit`); never edit them by hand, and run it (and commit its output) after changing a role. `sdkit dev adapters --check` must be clean.
- **Roles stay narrow**: independent roles (`verifier`, `reviewer`, `security-auditor`) are `read-only`; `test-writer` edits tests only; the implementer never verifies. Roles declare a cost `tier`, never a model name. Keep the verifier's
  `DOD / FINDINGS / VERIFY / VERDICT` format exact, `spec-driven-dev` depends on it.
- **Keep `SKILL.md` short.** Step detail lives in `skills/spec-driven-dev/references/` and is read only at the step that needs it (token economy). Skills must stay host-neutral: host-specific tool names go through `references/hosts.md`. Skills and roles call `sdkit <command>`, never a path to a script, so the same text works in bash, PowerShell and cmd.
- **`spec-driven-dev` writes no spec and calls no OpenSpec skill.** The spec comes from the analyst side (`generate-specs`, `update-specs`, `merge-specs`, which alone use OpenSpec) or, standalone, is the approved `plan.md`. Do not add spec authoring to it.
- **Code rules** (details in `docs/go-port/01-architecture.md`): a package takes its inputs as parameters; only `cmd/` and `internal/hook` read stdin, `os.Args` and the environment. Settings reach packages as a struct built by `envfile`, never by scattered `os.Getenv`. No `os.Exit` outside `cmd/`; return errors. JSON that is hashed or committed uses structs or an ordered writer, never `map` iteration. Process and path code must work on Windows (`proc_unix.go` / `proc_windows.go`, `filepath`, no shell-outs to `sh` for kit logic). Comments say why, not what; keep each command's usage in its header comment.
- **Tests are few and aimed at decisions** (`docs/go-port/04-testing.md`): table tests for pure decision logic (a new bug is a new row), a golden file only for output that skills or docs quote, and five scenarios with the real binary in a temp git repo. No test for plumbing, help text, template text or documentation counts. Keep the whole suite under 20 s, with no Docker and no `jq`.

## When you change something

- Keep the numbers and tables in sync in one change: skill/role/hook counts, the list of `sdkit` subcommands and the settings list appear in `README.md`, `core/roles/README.md`, `docs/guide.md`
  (§2, §6, §7, §10, §15) and `docs/cheatsheet.md`.
- Version bumps go in **both** `.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json` (the binary reads its version from the embedded `plugin.json`), plus the version badge at the top of `README.md`.
- Docs: `README.md` short; `docs/` English; details live in `docs/guide.md` and other files link to it instead of repeating it.
- Commits follow `core/rules/git.md` (`<type>(<scope>): <description>`, imperative, ≤ 72 chars).

## Checking a change

Run, from the repo root: `gofmt -l .` (prints nothing), `go build ./...`, `go vet ./...`, `GOOS=windows go vet ./...`, `go test ./...` (the whole suite, about 20 s; there is no test selection), `sdkit dev adapters --check` (`go run ./cmd/sdkit dev adapters --check`) and `go run ./cmd/sdkit dev scan` (the tree is safe to publish). Exercise a hook by piping a sample tool-call JSON into `go run ./cmd/sdkit hook <name>` (both a case that must trigger and one that must not). For `init`/`doctor`, run them against a scratch `git init` directory. `JSON` files you touch: validate them (`go run` or any JSON tool; `jq` is not a kit dependency). See `CONTRIBUTING.md` for the commands. `bench/` was moved to `attic/bench` and is not maintained or built.
