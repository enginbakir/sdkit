# Release, packaging and cutover

Nothing here is done without the user's explicit go-ahead: no tag, no push, no publish, no version bump (README, "What you must not do"). The orchestrator prepares everything and stops at the first irreversible step.

## Artifacts

- **GoReleaser** (`.goreleaser.yaml`, P0-06, finalised in P5-03) builds `darwin/arm64`, `darwin/amd64`, `linux/arm64`, `linux/amd64`, `windows/arm64`, `windows/amd64`. Archives are `tar.gz` (zip on Windows) with a checksums file. The version string comes from the embedded `.claude-plugin/plugin.json` (single source, P0-01); no `-ldflags` injection, so the tag must match `plugin.json`.
- `kit.go` embeds `core skills agents adapters stacks templates`, so the binary is the whole kit. `sdkit where` prints the install location of the binary (for the git-hook shims and docs) and `sdkit version` the version. The data is read from the embedded FS; `sdkit init` writes it out. The repo keeps these directories as real files too, because the Claude Code plugin is installed from git.
- The plugin (`.claude-plugin/`, `skills/`, `agents/`, `hooks/hooks.json`) stays in the repo. Its hooks call `sdkit hook ...`, so **`sdkit` must be on `PATH`**. `sdkit doctor` and the `check-tools` hook say so when it is not, and compare the plugin version with the binary version.

## Packaging

| Channel | What |
|---|---|
| Homebrew (macOS, Linux) | the formula downloads the release binary for the platform; `depends_on "node"` only (no `jq`). `Formula/sdkit.rb` and `packaging/homebrew/` are regenerated by the release pipeline; `gen-formula.sh` is retired |
| Windows | release zip, and a **Scoop** manifest (`packaging/scoop/sdkit.json`). `winget` later (D10). `sdkit.exe` on `PATH` is the only requirement besides `git` and `node` |
| Source | `go install github.com/wecii/sdkit/cmd/sdkit@<tag>` works because the module is at the repo root |

Prerequisites for users: `git`, `node` (OpenSpec), the stack's toolchain; `gh` or `glab` for GitHub or GitLab PRs. `jq`, `bash` and `python3` are no longer prerequisites.

## CI gate (server side)

Today the CI job runs the **base branch's** `sdd.sh`, so a pull request cannot edit the check that judges it. In 2.0:

- `templates/ci/*.yml` install a **pinned release version of `sdkit` with a checksum**, then run `sdkit sdd ci-check`.
- The pinned version is read from the **base branch's** CI file or settings, never built from the PR's code.
- A PR whose code change has no committed attestation for exactly that diff fails; medium and high also need a verifier PASS.
- Scenario B proves the property with a PR that tries to lower the version or edit the check.

## The kit's own CI (`.github/workflows/go.yml`, P0-06)

Matrix `ubuntu-latest`, `macos-latest`, `windows-latest`: `go build`, `go vet`, `go test -race ./...`. Windows job also runs `tests/windows-smoke.ps1` once P2 lands. A release workflow (manual, tag-triggered) builds the artifacts but publishes nothing until the user enables it.
